## A：計測と記録の信頼性

### R2-A01 SDの部分書き込みとヘッダ書き込み失敗

- 根拠: [SDManager.cpp](../src/SDManager.cpp) 68〜80、140〜163行。本文は `bytesWritten == 0` のみで失敗判定し、ヘッダ・開始時刻コメントの `println()` 戻り値は確認しない。
- 発生条件・影響: 容量不足などで必要なバイト数の一部だけを書いた場合、CSVが途中で切れても成功になる。ヘッダ作成に失敗してもファイルが開ければ記録を開始する。0バイト失敗に対するERR表示は修正済みなので、その成果とは区別する。
- 修正案: 改行を含む期待バイト数と実際の書き込み数を比較し、ヘッダ・本文の全経路に適用する。バッファへの書き込み成功と媒体への永続化も区別し、使用ライブラリで検出できるエラーを整理する。SDのみ停止してMQTTを継続する状態を明示し、停止／再開始、再マウントが必要な場合の復旧手順を定義する。
- 確認方法: open失敗、0バイト、期待値未満の正のバイト数、ヘッダ失敗、容量不足を注入して、成功表示にならないこと。現在の `sd_available` は起動時判定のままで、自動復旧は実装されていない。

### R2-A02 サンプルの取得時刻が保存・送信されない

- 根拠: [main.cpp](../src/main.cpp) 169〜185、270〜275行では取得時刻をキューで渡す。一方、[StateManager.cpp](../src/StateManager.cpp) 126〜135行は圧力値だけを保存・送信へ渡し、[SDManager.cpp](../src/SDManager.cpp) 151行と[MQTTManager.cpp](../src/MQTTManager.cpp) 86行で現在の `millis()` を取り直す。
- 発生条件・影響: 例えば2秒分のキューが滞留すると、2秒前の圧力を現在付近の時刻で記録する。キュー処理を速めても取得間隔を復元できず、センサー変化と外部事象の時刻がずれる。
- 修正案: サンプル取得時刻をSD・MQTTまで引き継ぐ。CSVの相対時刻は明確な記録開始基準から算出し、MQTTも取得時刻と必要なら送信時刻を区別する。開始前データの扱いはR2-A03と合わせる。
- 確認方法: 意図的に消費側を停止・再開し、保存された時刻が実際の取得時刻を保つこと。遅延、欠測、`millis()`の周回時も時系列の扱いを確認する。

### R2-A03 記録境界とキューのサンプルが対応していない

- 根拠: [main.cpp](../src/main.cpp) 169〜185行で状態によらず取得し、254〜275行ではボタンによる状態遷移の後にキューを消費する。[StateManager.cpp](../src/StateManager.cpp) 112〜135行は取得時ではなく消費時の `currentState` で保存を決める。
- 発生条件・影響: キューに待機中のデータが残っている状態でREC開始すると、その古いデータが新しいCSVへ保存される。REC停止時は、停止前に取得済みでもキューに残ったデータが保存されない。滞留が大きい場合、停止・再開始で前回分が次のファイルへ入る可能性もある。
- 修正案: 記録開始・停止の取得時刻境界、または記録セッションIDをサンプルと対応付ける。開始前は保存せず、停止前に取得した対象データを排出してから記録を確定する。単純な全キュー破棄でよいかも記録要件として決める。
- 確認方法: キューに既知の値と取得時刻を残し、開始・停止・再開始を繰り返す。開始前の値が混入せず、停止までに記録対象となった値の扱いが仕様どおりであること。

### R2-A04 同期I/Oがメインループに残り、4件制限では処理時間を制限できない

- 根拠: [main.cpp](../src/main.cpp) 254〜282行、[StateManager.cpp](../src/StateManager.cpp) 126〜135行、[SDManager.cpp](../src/SDManager.cpp) 140〜163行、[MQTTManager.cpp](../src/MQTTManager.cpp) 76〜99行。
- 確定している構造: 再接続処理は別タスクだが、SDのopen／write／closeとMQTTの `client->publish()` はメインループ側で実行する。mutexを待たずに取得できても、その後の送信自体は同期処理である。ローカルSDKの `send_ssl_data()` にも書き込み待機ループがあり、MQTTの `setSocketTimeout(3)` だけでTLS書き込み全体が3秒以内になるとは言えない。
- 影響・未検証事項: 遅いSDや送信詰まりではボタン更新が遅れ、サンプル消費も止まる。実機での最大遅延・欠落頻度は未測定。空の512件キューが全く消費されなければ約5.12秒で満杯になる。部分的に消費できる場合の増加速度は生成速度と消費速度の差になる。
- 修正案: MQTT送信を通信タスクへ集約し、保存もUIから分離して有界キューで渡す。SDファイルは記録中保持し、バッチ書き込み・定期flush・停止時closeの方針を決める。キュー使用量と欠測をセッションに対応付けて観測する。
- 暫定措置: ユーザー承認済みの `max_samples_per_loop = 4` を不適切として撤回する指摘ではない。これは件数制限であり時間制限ではない。平均100 samples/sを消費するには、最大4件ずつなら毎秒25周以上が必要で、一時的な遅延にも余裕が必要。
- 確認方法: SD遅延、MQTT送信停滞、再接続、一定値描画を組み合わせ、取得間隔、キュー最大使用量、あふれ、Aボタン応答時間を測る。許容基準を決めてから完了判定する。

### R2-A05 ADCの運転中障害に対する期限・有効性判定がない

- 根拠: [main.cpp](../src/main.cpp) 169〜186行は読み取り結果を無条件に圧力へ変換する。固定サブモジュールの [Adafruit_ADS1X15.cpp](../lib/Adafruit_ADS1X15/Adafruit_ADS1X15.cpp) 115〜127行は変換完了まで期限なしで待機し、382〜402行はI2C read/writeの成否を呼び出し元へ返していない。
- 発生条件・影響: 起動成功後のADC抜去やI2C異常を `adc_available` へ反映できない。変換完了ビットが得られない場合は計測が停止し得る。転送失敗時の具体的な値や再起動の有無は実機依存であり、常に特定値になるとは断定しない。
- 修正案: 成否を扱える読み取り経路と変換完了の期限を設け、無効サンプルを保存・送信対象から除外する。異常表示、計測停止、再初期化の方針を決める。圧力の範囲外フラグを追加する提案ではなく、通信として値を取得できたかの判定である。
- 確認方法: 正常起動後にADCを切断し、期限内にエラーとなること、正常データとして記録しないこと、UIが操作可能なことを確認する。

### R2-B02 NTPの待機・復旧が通信保守も遅らせる

- 根拠: [TimeManager.cpp](../src/TimeManager.cpp) 39〜65行、[main.cpp](../src/main.cpp) 190〜205、224〜227行。10回の試行それぞれで既定タイムアウトの `getLocalTime()` と1秒のdelayを呼ぶ。ローカルSDKの既定待機は5秒で、未取得時には合計約60秒になり得る。
- 影響: オフライン起動後の再試行は30分間隔。遅れてSNTPが成功しても `time_synced == false` が残る。起動時は計測タスク生成前に同期を待ち、運転中の再同期はMQTT保守と同じネットワークタスクで待つため、その間MQTTのloop処理も遅れる。
- 修正案・確認: Wi-Fi復旧を契機に同期し、短い確認タイムアウトと実時間の期限を使う。遅延成功を状態に反映する。オフライン起動、NTP不達、遅延成功で計測開始とMQTT接続維持への影響を測る。

- 修正案・確認: 列ごとの最小／最大値を保持し、必要な時間分解能に応じて取得時刻で列を決める。欠測は欠測として表示する。同一列内の短いパルスと意図的な取得欠落を与え、移動空白帯も維持できることを確認する。

- 修正案・確認: 完全な日時・連番・サイズを確認できる削除画面とキャンセル操作を設ける。成功・失敗を画面へ反映する。同日の複数ログと削除失敗を確認する。

### R2-B07 キュー・タスク・mutex生成失敗が動作可否へ反映されない

- 根拠: [main.cpp](../src/main.cpp) 239〜251行はキュー失敗をシリアルに出してsetupから戻るだけで、タスク生成結果は検査しない。[MQTTManager.cpp](../src/MQTTManager.cpp) 6行のmutex生成結果も検査しない。
- 発生条件・影響: メモリ不足等で計測タスク生成に失敗してもADC初期化成功の表示が残り、REC開始操作を受け付け、データ行の増えない記録になり得る。キュー生成失敗でも同様に機能全体の利用不可状態にならない。無効なmutexの利用も防げない。
- 修正案・確認: 各生成結果を検査し、センサー初期化成功と計測系起動成功を区別する。計測系が使えない場合はRECを抑止し、原因を表示する。生成失敗を注入して確認する。

### R2-B08 MQTTの送信判定・送信・時刻更新が一体になっていない

- 根拠: [StateManager.cpp](../src/StateManager.cpp) 133〜135行が `canPublish()`、`publishData()`、`updateLastSendTime()` を順に呼ぶ。[MQTTManager.cpp](../src/MQTTManager.cpp) 76〜116行ではそれぞれ個別に待機なしでmutexを取得し、送信関数は結果を返さない。
- 発生条件・影響: 判定成功後に別タスクがmutexを取得するとPublishがスキップされる。その後の時刻更新だけ成功すると、未送信でも送信済み時刻を進める。逆に送信後の時刻更新だけ失敗すると、次の送信を500 ms待たずに試す可能性がある。通常のPublish失敗時も時刻は更新される。さらに間隔判定はサンプル取得時刻なので、滞留データの高速処理時には実時間の送信間隔とは一致しない。
- 修正案・確認: 通信タスクで送信判定・結果・成功時刻を一元管理する。試行間隔と成功時刻を分け、画面の接続状態も同期されたスナップショットとして提供する。mutex競合・Publish失敗・キュー滞留を模擬して確認する。
- 要件: 100 Hzの全サンプルをクラウドへ届ける仕様ではなく、現状は約500 ms単位の配信である。最新値配信か履歴配信かを明確にし、必要に応じて取得時刻・セッションID・連番を追加する。再送・重複排除は完全配信が必要な場合に設計する。

### R2-B09 回帰テスト・CI・依存環境固定

- 根拠: [platformio.ini](../platformio.ini) 11〜18行。プラットフォームはバージョン未指定、依存ライブラリは範囲指定。追跡対象の `test/` はREADMEのみで、`.github/workflows/` はない。ADSライブラリはサブモジュールで固定済み。
- 影響: 今回のローカルビルド成功だけでは、新規環境の再現性や状態遷移・書き込み異常の回帰を保証できない。
- 修正案・確認: 検証済みバージョンを固定し、非秘密の設定でCIビルドする。部分書き込み、記録境界、時刻伝搬、生成失敗、表示キャッシュなど振る舞いを検証するテストを追加する。実機でしか測れない周期・SD遅延は別の試験記録にする。
